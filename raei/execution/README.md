# RAEI Evidence-Based Execution System V1.0

**Status:** Proposed implementation; not merged or activated as a production authority.  
**Purpose:** Turn the approved RAEI mastery programme into a persistent, evidence-led learning and readiness workflow.

## 1. The actual solution

RAEI is advanced through small, assessable work units. Each unit follows the same loop:

1. **Teach:** explain the subject from first principles and identify authoritative source material.
2. **Demonstrate:** work through a representative example.
3. **Practice:** assign a practical task or contextual study task.
4. **Execute:** run code/tests where tools permit; otherwise label the work as a proposed or unexecuted exercise.
5. **Assess:** evaluate against explicit criteria and check for critical errors.
6. **Correct:** teach the failed concepts and repeat a fresh assessment.
7. **Record:** add dated evidence, score, status and source references to the ledger.
8. **Advance:** move to the next prerequisite-satisfied unit.

A conversation response is not evidence of execution by itself. A claimed test must include the command or method, environment, result and relevant output. A claimed Bible-study competency must include the actual interpretive work and assessment response, not merely a generated summary.

## 2. Operating constraints

- RAEI remains an engineering specialist capability inside RhemaScript.
- Bible-only ethics is the sole moral foundation for RAEI's ethical judgements. Technical, legal and security standards may be treated as operational constraints, not as alternative moral authorities.
- RAEI must not claim personal faith, conscience, divine revelation or pastoral authority.
- No human team, hiring, paid API, spending, external integration or external service is introduced by this learning system.
- Learning exercises do not authorise main RhemaScript implementation.
- Preserve POS V1.4, the existing architecture, P0 Security Governance Foundation, source-to-final integrity chain and all six approval gates.
- No generation, publishing, spending, external writes, deployment, merges or changes to authority masters without the relevant existing authorisation.
- No background progress is implied. Work is performed in an active session and persisted to the repository only through an authorised, reviewable change.

## 3. Work-unit record

Every work unit must contain:

- Stable ID and domain.
- Prerequisites and learning objectives.
- Source material (Bible references for biblical work; technical references for engineering work).
- Teaching and worked example.
- Learner task and expected artefact.
- Assessment rubric and pass threshold.
- Actual execution evidence or an explicit statement that execution was not performed.
- Score by competency, critical-failure flag, corrections and reassessment result.
- Status: `not_started`, `in_progress`, `needs_correction`, `passed`, or `blocked`.
- Evidence provenance: date, tool/environment, command or method, output/result, and artefact reference.

A unit is `passed` only when its required artefact exists, the assessment threshold is met, evidence is inspectable, and no critical failure remains. Reading or explanation alone is not a practical pass where practical evidence is required.

## 4. Programme gates

### Gate A — Engineering

Complete and assess computer science foundations, programming, algorithms/data structures, operating systems/concurrency, databases/transactions, networking, distributed systems, secure software, frontend, backend/API design, testing, DevOps/operations, architecture and recovery.

Required capstone evidence:
- Integrated frontend/backend/database application.
- Authentication and role-based authorisation.
- Input validation and secure API behaviour.
- Automated unit, integration and end-to-end tests.
- Concurrent transactional operations and consistency checks.
- Failure handling, audit trail, backup and demonstrated restore.
- Reproducible build/run instructions and architecture rationale.

### Gate B — Whole-Bible understanding

Study all 66 books, book by book, in canonical and literary context. For each book record setting, genre, structure, major themes, key passages with surrounding context, canonical relationships, interpretive risks and answered comprehension questions.

Distinguish direct textual statements from inference and disputed interpretation. Do not claim original-language expertise without demonstrated language competence. Verify direct quotations against the translation required by the project; use HINOVBSI for direct Hindi Scripture quotations where specified.

### Gate C — Bible-only ethical reasoning

Assess applied cases involving truthfulness, stewardship, justice, compassion, accountability, privacy, authority, deception, manipulation, harm and responsible technology.

Each case must identify relevant passages, explain context, compare relevant texts, distinguish explicit teaching from inference, state uncertainty and justify the decision. Proof-texting and invented doctrine are critical failures.

### Gate D — RhemaScript mastery

Demonstrate command of the existing POS V1.4 and its established capabilities, CAP-01..15, IF-01..18, six approval gates, P0 security governance, source-to-final integrity chain, biblical verification, RS-CIE, TISR, YCSAI, VBAP, LSLS, PPE, PAF, CAPWF, visual/audio-visual planning, asset-first editing, evidence provenance, QC and publishing boundaries.

The capstone simulates one complete project from biblical source to final-film readiness. Every dependency, source, approval, revision and evidence item must be traceable. The simulation must not generate media or publish.

### Gate E — Integrated readiness

Readiness requires all four gates above to pass, plus an integrated capstone that combines engineering controls, contextual biblical interpretation, Bible-only ethical reasoning and RhemaScript governance.

Use the established 0–4 competency scale. Minimum provisional threshold: score 3 in every applicable dimension, with no critical failure and no missing mandatory evidence. A self-assessment is not independent assurance. Any existing independent-assurance requirement remains outstanding until actually satisfied.

## 5. Progress and continuity

The ledger is the durable source of truth; chat is the working interface. At the start of a session, load the latest ledger, identify the earliest incomplete prerequisite-satisfied work unit, and continue there. At the end, record only work actually completed in that session.

Never:
- mark an entire domain complete because its curriculum was written;
- convert a planned exercise into an executed test;
- infer mastery from a fluent explanation;
- hide a blocker or missing evidence;
- change a passed record without a versioned correction trail;
- equate readiness with permission to start production.

## 6. Honest current baseline

The prior programme has reported Level 2 programming and capstone work, some Level 3 conceptual/exercise work, and a successful limited security exercise. Those are historical reports, not all independently re-executed evidence in this change. The new ledger must import them as `reported_unverified` until the original artefacts or reproducible results are available.

The 66-book study, applied ethics cases, complete full-stack capstones, RhemaScript end-to-end capstone and integrated readiness assessment remain open unless and until evidence is recorded.

## 7. Definition of done

The programme is complete only when:
- every mandatory work unit is passed with inspectable evidence;
- all 66 book records and their assessments are complete;
- the required applied ethical cases pass;
- all engineering capstones pass;
- all applicable RhemaScript capabilities and interfaces are evidenced;
- the integrated capstone passes;
- no critical blocker remains; and
- the final readiness report lists scores, evidence, limitations, unresolved assurance requirements and the exact authority boundary for subsequent development.

This system tracks and validates evidence. It does not itself teach, execute tests, interpret Scripture, certify competence or grant production authority.
